# AGENTS.md

## Project

Android app (`:app`, package `com.kienhoang.dualsubreplay`) with a separate test-only `:benchmark` module: Kotlin 2.3.21, Jetpack Compose / Material 3, AGP 9.3.2, committed Gradle 9.5 wrapper (no local Gradle needed), JDK 17, compile/target SDK 36, minSdk 26.

## Commands (Windows)

```powershell
.\gradlew.bat formatCheck complexityCheck testDebugUnitTest lintDebug assembleDebug assembleDebugAndroidTest   # CI parity
.\gradlew.bat pixel2Api36DebugAndroidTest                                          # instrumented tests on managed device
.\gradlew.bat testDebugUnitTest --tests "com.kienhoang.dualsubreplay.data.SubtitleMergerTest"   # one test class
```

- Managed-device tests require the API 36 AOSP x86_64 system image. On headless hosts add `-Pandroid.testoptions.manageddevices.emulator.gpu=swiftshader_indirect` (CI also passes `--no-parallel --max-workers=2`).
- Debug APK output: `app/build/outputs/apk/debug/app-debug.apk`.

## Development workflow

1. Before significant work, read [mission](docs/project/mission.md), [technical context](docs/project/tech-stack.md), [ROADMAP.md](ROADMAP.md), relevant specs, and relevant source/tests. Stable intent belongs in the repository, not only chat history.
2. Create/update a [feature spec](docs/specs/README.md) with acceptance criteria, a small plan, and validation scenarios **before coding**. New features, significant/risky fixes, architecture, migrations, CI/release changes, and measurable performance work need specs; trivial changes need only a clear PR and acceptance criteria.
3. Record release intent before implementation where possible and resolve it before opening the PR. Existing owner authorization covers the agreed implementation; do not add a redundant approval round or invent approval. Ask about unresolved material scope/product decisions.
4. Implement the smallest coherent solution and validate against the criteria. Record actual implementation, deviations, and passed/failed/unverified checks in the spec. Offline tests do not establish physical-device or live-YouTube success.
5. Update relevant permanent docs in the same PR when an authorized decision changes architecture or conventions. Keep ROADMAP.md directional and each implementation plan inside its feature spec; keep QA evidence in docs/qa/.
6. Open a focused PR against `main` linking the spec (or explaining why none is needed). Open it ready for review, never as a draft: the owner wants to test and merge without extra GitHub steps, and marking a draft ready restarts CI. The owner remains final merge authority; do not merge, enable auto-merge, or publish releases unless explicitly instructed.

## Preparing PRs for owner merge

- Read `.github/workflows/release-on-main.yml` and `tools/automatic_release.py` before handoff; they define actual automation. Use the [release-intent mapping](docs/specs/README.md#release-intent-is-a-decision-not-automation).
- Follow explicit owner release intent; otherwise preserve **patch**, including workflow PRs. Recommend alternatives if useful, but do not silently infer minor/major. **Standing owner decision (2026-10-04): apply `release:skip` without asking when every changed file is documentation or promo media** (`*.md`, `docs/**`, `site/**`, `tools/promo-video/**`, `.github/ISSUE_TEMPLATE/**`, `.github/pull_request_template.md`), **extended 2026-10-17 to website-only PRs that also change the website's test or workflow** (`tools/tests/test_site.py`, `.github/workflows/pages.yml`). If any other file changes (app or test code, Gradle, workflows, release tools) or you are unsure, keep patch and ask.
- Apply and verify the actual GitHub label or standalone exact-version PR-body directive. Prose/specs/checkboxes do not apply labels. Keep at most one release label OR one directive; remove superseded overrides without disturbing unrelated labels. If required metadata cannot be applied, report the missing action and do not call the PR ready to merge.
- State intent, reason, and expected version (or why skipped/unavailable). Inspect stable tags, releases including draft reservations, and the Gradle baseline before estimating. Bump-derived numbers are estimates until reserved; exact versions must exceed all existing/reserved stable versions. Do not manually change Gradle versions or create release tags in normal PRs.
- When the final-head CI passes, send the owner the preview release page link, https://github.com/hoangkien1703/dual-sub-replay/releases/tag/preview, so they can test on a phone before merging. **Never send a direct `.apk` download link** (owner decision 2026-10-08): the owner can't download from it and downloads the APK from the release page themselves. `pr-preview-auto.yml` uploads it to that rolling `preview` release as `DualSub-Replay-PR<N>-build<run>-preview.apk`, so name the asset to pick; a newer build of the same PR replaces the older asset.
- Before calling a PR ready to merge, verify its latest final-head Android CI run: both jobs (`verify-build`, `managed-device-tests`) must succeed. New commits need fresh checks; report pending/failed/skipped/unavailable checks explicitly.
- Handoff: owner reviews the preview and green checks, then manually merges; existing automation publishes unless skipped. Green PR CI is not proof of release publication. Verify the release workflow/assets if asked to confirm publication; use existing reservation/retry recovery below.

## Releases happen automatically after an approved PR merge

- When `hoangkien1703` merges a PR into `main`, `release-on-main.yml` checks the latest Android CI run for the PR's final head and requires both Android CI jobs (`verify-build`, `managed-device-tests`) to succeed. Direct pushes and other mergers do not release. Android CI also runs on every push to `main` so `setup-gradle` saves fresh caches for PR runs; those runs never count as PR CI.
- Default: bump the highest existing/reserved stable patch version and monotonically increase Android `versionCode`. **Do not manually bump Gradle version constants in feature PRs.**
- Before merge, apply at most one GitHub label (`release:patch`, `release:minor`, `release:major`, `release:skip`) OR a standalone `Release-Version: X.Y.Z` in the PR description. Conflicting instructions fail closed. `release:skip` publishes nothing.
- Release versions live in a release-only commit/tag based on the exact merge; only the two Gradle version constants change. `main` keeps development defaults. No bot commits to `main` or branch-protection bypass is needed.
- Draft release metadata reserves version/name/code/source before building. Retry failed runs (or dispatch with a merged PR number) to resume that reservation. Never delete reservations or edit their hidden marker to retry. Published merges are a no-op.
- Production signature, package, and version are verified before upload; the draft is published only with both APK and checksum present. Release notes are generated automatically. Queued runs cannot allocate the same version, and older retries cannot replace a newer Latest release.
- Merges into `main` publish no preview APK (owner decision 2026-10-18); the `preview` release holds only open PRs' `DualSub-Replay-PR<N>-build<run>-preview.apk` builds. The PR CI artifact stays `DualSub-Replay-preview`, the name `pr-preview-auto.yml` downloads.
- Release builds require the four `ANDROID_RELEASE_*` env vars plus `-PrequireReleaseSigning=true`. Never commit signing material (`*.jks`/`*.keystore` are gitignored).
- Test workflow changes with `python3 -m unittest discover -s tools/tests -p 'test_*.py' -v` and validate workflow YAML/shell. These tests also run in Android PR CI.

## Architecture invariants (enforced by tests)

- Exactly one WebView exists (`SingleYouTubePage` in `ui/YouTubeBrowserScreen.kt`). YouTube tabs (owner request 2026-10-27, [spec](docs/specs/2026-10-27-youtube-tabs.md)) are saved addresses (`ui/BrowserTabs.kt`) loaded one at a time into that page, so only the open tab plays; with every tab closed the page leaves composition and an empty page offers a new tab. A tab of another Google account (Settings → YouTube tabs → Use different Google accounts, off by default) replaces the WebView, because a WebView profile must be set before the WebView loads anything (`ui/YouTubeTabAccounts.kt`); use the tab's `tabCookieManager`, never `CookieManager.getInstance()`, in the page. Online replay seeks the native YouTube page video via a JS polling bridge. Offline video downloading and local Media3 playback are removed; never add a second online player/WebView.
- Screen-off playback and earphone controls (owner decision 2026-10-13): `playback/WebVideoPlaybackService.kt` is a `mediaPlayback` foreground service owning a media session and notification that only send play/pause/seek scripts to the page video; it is not a second player. The YouTube page is always told it is visible (`WEB_KEEP_PLAYING_WHEN_HIDDEN_SCRIPT`), so videos keep playing with the screen off for every account. See the [spec](docs/specs/2026-10-13-background-play-and-earphone-controls.md).
- Main-frame navigation goes through `classifyMainFrameUrl` → `YOUTUBE_WEB` (embed) / `GOOGLE_SIGN_IN` (embed during sign-in flow) / `OPEN_EXTERNAL` (browser) / `BLOCK`. JS snapshot/replay scripts must keep re-verifying the executing origin (`https:` + `*.youtube.com`); `PlaybackArchitectureTest` asserts the literal script text.
- Caption discovery uses watch-page metadata and undocumented Innertube player fallbacks, then timed-text downloads, isolated behind `data/CaptionProvider.kt` / `YouTubeCaptionProvider.kt` (host allowlist, 8 MiB response cap). Keep that replaceable boundary. The YouTube page fetches the track first (owner decision 2026-10-18, [spec](docs/specs/2026-10-18-page-first-full-transcript.md)): `PageFirstCaptionProvider` races the page (`PageTranscriptSource`, scripts in `YouTubeWebScripts.kt`) against that download; the first success wins. The page keeps a copy of the caption replies its own player downloads (`WEB_CAPTION_CAPTURE_SCRIPT`, a document-start script that only reads `/api/timedtext` and `/youtubei/v1/get_transcript` replies on YouTube hosts and never changes a request), so the app never re-sends the page's token; captions the player loads later still replace live subtitles. An empty track list in the player's details is no dead end: the player's captions menu and its downloads count too. As the last resort (owner decision 2026-10-18) the page opens YouTube's own transcript panel and takes its lines. With Settings → Study tools → Load captions with a page token (beta, owner request 2026-10-20: Automatic by default, On, Off), a page whose plain request comes back empty mints its own proof-of-origin token as YouTube's web player does (`ui/PageTokenScript.kt`; BotGuard's interpreter only from `https://www.google.com/js/th/`) and asks again with `pot`; once that worked, Automatic asks with the token first on later videos (`page_token_needed`) until a plain request works again, and On always asks with it first; the token never leaves the page and `webPageTranscriptScript` keeps its one `fetch(`.
- Translation uses Google Translate's unofficial web endpoint by default (`translation/GoogleWebTranslator.kt`, owner decision 2026-10-05); Settings → Translation switches to on-device ML Kit (`translation/OnDeviceTranslator.kt`). No user-provided/developer-provisioned service key is ever required. Settings → Translation → Translate with AI (beta, off by default, owner request 2026-10-28, [spec](docs/specs/2026-10-28-ai-subtitle-translation.md)) lets the AI assistant's service, model and keys translate first (`translation/AiSubtitleTranslator.kt`: windows of sentences split into their rows plus earlier sentences as context, one translation per row in JSON); Google translates whatever it leaves out or when it fails or is slower than 6 s, and the assistant cannot change this setting. When Google still fails after its retries (1 s, 3 s, 7 s; none for a block), that video uses YouTube's own translated captions, as LingoTube does (owner decision 2026-10-19, [spec](docs/specs/2026-10-19-youtube-translation-fallback.md): the page fetches the track with `tlang`, `PageTranslationSource`), and quietly translates on-device what YouTube does not cover; a top-right icon explains why (naming the Google address and status), and Google is checked again every 2 minutes and on every load. A row never waits long for Google (owner decision 2026-10-19, [spec](docs/specs/2026-10-19-quick-switch-when-google-is-slow.md)): after Settings → Translation → Wait for Google (Automatic: 2 s on mobile data, 4 s on Wi-Fi; or 2, 4, 8 s) the video switches the same way while Google's request runs on, and goes back to Google, replacing the shown lines, once it answers; an unreachable address hands over to the next, and the address that last worked is tried first, kept across restarts in `google_addresses` preferences for translation and voice alike (owner request 2026-10-19, [spec](docs/specs/2026-10-19-remember-working-google-address.md)); after a failure on mobile data the next load on mobile data starts without Google and checks it as soon as a row plays. A line Google leaves blank is asked again alone at each address and, if still blank, only that line translates on-device; a reply with every line blank counts as a refusal. While a video plays, minutes 2 to 5 are translated in the background, one request every 3 s (owner decision 2026-10-09, [spec](docs/specs/2026-10-09-google-blank-lines-and-five-minutes-ahead.md)); the current minute is translated also while paused (owner request 2026-10-27, [spec](docs/specs/2026-10-27-translate-while-paused-and-fullscreen-menu.md)). See the [Google Translate spec](docs/specs/2026-10-05-opt-in-google-translate.md).
- The AI assistant (`assistant/`, `ui/AiAssistant*.kt`, owner decision 2026-10-08) and the opt-in Translate with AI are the only features that use the user's own API key, for Gemini, OpenRouter, OpenAI, Claude (Anthropic's own Messages API), OpenCode Zen/Go, or an OpenAI-compatible HTTPS address. It is on by default, sends nothing until a key is added and a question asked, and More settings → AI assistant turns it off completely (the translation problem icon then returns). Keys are AES-GCM encrypted with an Android Keystore key in `ai_assistant_keys` preferences; keys, `files/ai-chats/` and `files/ai-memory/` (memories and the user's instructions) stay excluded from backups (`BackupRulesTest`). Chats are kept 7 days by default (Off / 7 / 30 days / Forever). Subtitle and error text, and attached text files, go to the model as quoted data; attached pictures and files stay in memory and are never written to chat history. Never add a project server or shared key. The assistant acts only through the fixed tool list in `assistant/AiActions.kt` (owner decision 2026-10-08): small setting changes, playback, speed and Save to vocabulary run at once with an Undo chip; YouTube search, opening a link the user typed, translation changes, and the settings that reload subtitles, download models or change the interface language (`AiSetting.asks`) wait for the user's tap, and so do setting changes after subtitles, files or error text were read. It reads and may change every setting on the settings page except the ones below ([settings spec](docs/specs/2026-10-16-translation-position-and-ai-settings.md)). Memory changes only through `save_memory` and `forget_memory`, offered only while memory is on for the chat; they run at once with Undo and Manage, except after other text, and never come from subtitles, files or error text (owner decision 2026-10-08, [memory spec](docs/specs/2026-10-08-ai-assistant-memory.md)). Without full access it can never touch keys, the AI settings, saved words, dragged positions, or Reset all settings. More settings → AI assistant → Permissions → Full access (off by default, owner request 2026-10-18) offers the `AI_FULL_ACCESS_TOOLS`: its own AI settings, adding a key the user typed, removing a key, finding, editing and deleting saved words, and resetting settings or subtitle positions; most run at once with Undo, removing a key and resetting always wait for a tap, and after subtitles, files, error text or saved words were read every change waits for a tap. Only tools offered with the question run. It never touches language downloads, the assistant switch or full access itself. Each service keeps up to 10 keys (`AiKeyStore`, the first under the old one-key names); a rejected, out-of-credit or rate-limited key hands the same request to the next key ([redesign spec](docs/specs/2026-10-18-ai-settings-redesign-keys-and-full-access.md)). Search and screen (owner decision 2026-10-18, [spec](docs/specs/2026-10-18-ai-web-search-and-screen.md)): `find_youtube_videos` searches YouTube's own web search (`data/YouTubeVideoSearch.kt`, free, no key, on by default) and only videos it found or links the user typed can be opened, each still waiting for the Open tap; web search (off by default) is the service's own (Claude `web_search`, OpenRouter's server tool, OpenAI's search model; paid to that service) or Tavily with the user's free key (`AiSearchKeyStore`, sealed like the AI keys in `ai_assistant_keys`); `look_at_screen` (on by default) copies the app window with the panel hidden and sends the picture once, never saved. Search results and screenshots are quoted data and count as other text, so later changes wait for a tap. See the [AI assistant spec](docs/specs/2026-10-08-ai-assistant-panel.md), the [actions spec](docs/specs/2026-10-08-ai-assistant-actions.md), and the [Claude and Gemini default spec](docs/specs/2026-10-11-gemini-flash-lite-default-and-claude.md).
- User-visible text lives in `app/src/main/res/values/strings_<area>.xml` (English, the default) with the same file in every translated `values-*` folder; never add a UI string literal in Kotlin. The offered interface languages are `APP_LANGUAGES` in `ui/AppLanguage.kt` and `res/xml/locales_config.xml`; with no saved choice the app follows the device. `AppLanguageTest` and lint `MissingTranslation` fail when a language lacks a string or a placeholder differs. Diagnostic exception text in `data/` and `translation/` stays English. See the [interface languages spec](docs/specs/2026-10-02-app-interface-languages.md).
- Chinese learner help (owner decision 2026-10-18, [spec](docs/specs/2026-10-18-chinese-learner-help.md)) bundles data files only: jieba's word list and HanLP's pinyin and traditional-to-simplified tables, extracted at build time into `assets/learner-data/` (`LearnerLanguageData` in `app/build.gradle.kts`). No jieba or HanLP code and no download. Words are spoken with Google Translate's online voice (`translation/GoogleWebSpeech.kt`) while Google translates subtitles, in every language since 2026-10-19 (owner decision, [spec](docs/specs/2026-10-19-google-voice-every-language.md)): three Google addresses, then the phone's voices; after no address answers, the phone speaks at once for 2 minutes. Chinese grammar points (`data/ChineseGrammarCatalogue.kt` plus rules in `ChineseGrammar.kt`) share `data/GrammarMatcher.kt` with Japanese and carry HSK 3.0 levels (1–6 and 7–9) from the GF0025-2021 grammar syllabus, or the HSK 3.0 word list for points it does not list; every point needs its own example sentence in `ChineseGrammarCatalogueTest` and its text in all 8 interface languages.
- English learner help (owner request 2026-10-18, [spec](docs/specs/2026-10-18-english-learner-help.md)) also bundles data files only: OpenNLP's English part-of-speech model and WordNet 3.1's word and irregular-form lists, extracted at build time into `assets/learner-data/`, plus the CEFR-J word levels committed in `app/src/main/learner-data/` (free for commercial use with citation; keep the citation in `THIRD_PARTY_NOTICES.md` and the licence screen). No OpenNLP or WordNet code. English grammar points carry CEFR levels from the CEFR-J Grammar Profile (the rule is in the spec); every point needs its own example sentence in `EnglishGrammarCatalogueTest` and its text in all 8 interface languages.
- Kanji details on the word card (owner request 2026-10-24, [spec](docs/specs/2026-10-24-word-meaning-and-kanji-details.md)) bundle data files only in `app/src/main/learner-data/`: `ja-kanji.txt` and `ja-kanji-strokes.txt` are made by `tools/kanji/build_kanji_data.py` from KANJIDIC2 and KanjiVG and stay CC BY-SA (keep the credits in `THIRD_PARTY_NOTICES.md` and the licence screen; Hán Việt corrections go in the script's `HAN_VIET_FIXES`). `ja-radicals.txt` and the memory stories `ja-kanji-stories-en.txt` / `-vi.txt` are the project's own (MIT): never copy WaniKani, Koohii or Kanji alive mnemonics. ## UI conventions

- Every screen, panel, dialog, sheet and overlay uses the app theme: `DualSubTheme` (`ui/theme/Theme.kt`): dark teal by default, or the App colors the user picked (Black, Navy, Slate, Plum, Forest, or Light), with the user's accent. The overlay on the video stays dark on every theme; subtitle and part-of-speech colors use darker shades on light cards (owner decision 2026-10-16). UI drawn outside `DualSubApp`, such as overlays that `LearningPlayerRoot` places beside it, wraps itself in `DualSubTheme`; otherwise Material's light purple defaults show (`AiAssistantPanelUiTest` checks the assistant panel's color).
- Take colors from `MaterialTheme.colorScheme` roles, never from Material's defaults or new hex literals. If a component needs a role that `dualSubColorScheme` leaves at Material's purple default (for example `tertiary`), set that role in `Theme.kt` instead of coloring the component directly. The amber/red problem tints in `OnlineTranslationNotice.kt` and `AiAssistantUi.kt` (darker on the light theme) are the only shared status colors. Check a UI change on the Light theme too.
- Before handing off a UI change, look at it in the screenshots the Compose tests save (`saveUiEvidence`) or on a device, and check that it matches the screens around it.

## Testing conventions

- Unit tests are plain JUnit4 — no Robolectric or mocking library. They call `internal` top-level functions directly (same package), so keep new logic in small testable `internal` functions. `org.json` is a unit-test-only dependency.
- `unitTests.isReturnDefaultValues = true`: Android framework calls return defaults instead of throwing in unit tests.
- Instrumented tests build Compose UI in isolation (`createComposeRule`) and WebView fixtures run offline — tests never hit the live YouTube site.
